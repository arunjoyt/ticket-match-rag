# Add hard-positive, hard-negative, and cross-cluster eval fixtures

The current seed data (`data/seed_manifest.json`, generated by `scripts/seed_helpdesk.py`) has 8 Duplicate Clusters of 4 members each and 16 Distractors (8 topically-adjacent-to-a-cluster, 8 pure noise). It's good ground truth for "does retrieval beat random unrelated tickets," but every cluster member already shares obvious surface vocabulary with its siblings (the `vpn-crash-after-update` cluster all say "VPN" and "update"/"patch"), and every distractor is topically distant enough from its cluster to be an easy negative (e.g. "VPN connects fine but is slow" next to "VPN drops after update"). Neither property is guaranteed to hold on the corpus this system will actually see once ADR 0002's dataset-scaling concerns bite (`docs/adr/0002-native-sparse-vectors-for-bm25.md`).

This matters because it's an established failure mode in the closest adjacent research area, duplicate bug-report detection: reported gains are often overstated when eval sets don't include true duplicates with low lexical overlap or true negatives with high lexical overlap — the dataset ends up only testing "beats random," which BM25-only or embedding-only retrieval both pass trivially. The eval harness (issue #2) needs ground truth that can actually distinguish whether the dense side, the sparse side, and the reranker are each pulling weight, not just whether the pipeline as a whole beats chance.

Decision: extend the seed dataset with three new fixture categories, and extend `seed_manifest.json` with a tag so the eval harness can slice metrics by category instead of only reporting an aggregate.

## New fixture categories

**Hard positives** — one additional 5th member per existing cluster (+8 tickets). Paraphrased to deliberately minimize shared vocabulary with its siblings while preserving the same root cause — e.g. the `vpn-crash-after-update` cluster's 5th member describes "corporate network client stops working every time a system patch lands" without using the words VPN, disconnect, or update where avoidable. Tests whether a true duplicate with near-zero lexical overlap still gets retrieved — this is where dense embeddings have to carry the match alone, since BM25/sparse will score it near zero.

**Hard negatives** — one additional near-miss distractor per existing cluster (+8 tickets). Reuses most of the cluster's vocabulary but changes the actual failure mode, not just the topic — e.g. "VPN takes 5+ minutes to establish a connection after the recent update" sits next to the VPN cluster (same trigger words: VPN, update) but describes a slow-to-connect problem, not a drops-after-connecting one, so it isn't Root-Cause Similar and shouldn't clear the Match Threshold. Distinct from the existing topically-adjacent Distractors, which are already easy to separate; these specifically stress the reranker's precision, since hybrid search will likely rank them high on lexical/semantic proximity alone.

**Cross-cluster confusables** (+2-3 tickets) — tickets that could plausibly be mistaken for a different cluster than any they're seeded near, e.g. something symptom-adjacent to both `sso-login-redirect-loop` and `password-reset-email-not-received` ("can't get into the portal, auth keeps failing"). Tests whether the system keeps two real clusters cleanly separated, not just whether it beats pure noise.

## Manifest schema addition

`seed_manifest.json` gains a tag on each entry so the eval harness can slice metrics instead of only reporting an aggregate:
- cluster members: `"variant": "standard" | "low-lexical-overlap"`
- distractors: `"kind": "topic-adjacent" | "near-miss" | "pure-noise" | "cross-cluster-confusable"`

## qrels and metric slicing

For `ranx` (per the `eval_harness_design` memory's choice of IR-metrics library): held-out-one-member-as-query, same-cluster members are relevant (grade 2), everything else is not relevant (grade 0) — this is the existing Duplicate Cluster ground-truth definition from `CONTEXT.md`, unchanged. What's new is reporting precision@k/MRR/nDCG broken out by the `variant`/`kind` tags above, not just in aggregate. An aggregate number can look fine while masking that hard positives never surface or near-misses leak past threshold — the breakdown is what shows whether the dense+sparse+rerank stack is earning its complexity or whether one stage is doing all the work silently.

## Considered alternative

Leave the existing dataset as-is and rely on the LLM-as-judge component (scoped for later per `eval_harness_design` memory) to catch precision failures qualitatively. Rejected: the judge is scoped as a sampled, tiered check on top of the IR metrics, not a replacement for them, and it can't tell you whether a *specific, known* hard case was retrieved — only ground-truth qrels with labeled categories can answer that directly and cheaply on every eval run.

## Consequences

+18-19 tickets on top of the current 48, added the same way as the existing seed data (extend `CLUSTERS`/`DISTRACTORS` in `scripts/seed_helpdesk.py`, rerun against the local Docker Helpdesk instance, which regenerates `seed_manifest.json`). No changes to the ingestion or retrieval code — this is eval ground truth only. The eval harness itself (metric computation, `ranx` wiring, per-category reporting) is separate work under issue #2 and not built by this ADR.
